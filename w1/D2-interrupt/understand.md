## 1. 一句话版本（TL;DR）

中断 = **硬件主动打断你**（事件驱动）；轮询 = **你反复去问**（忙等）。ISR 只允许做「最短的事」（置标志/记时间）。防抖 = 对按键物理抖动这个噪声做**时间过滤**。

---

## 2. 详细版（为什么这样设计）

### 2.1 轮询 vs 中断——CPU 的两种等待方式

**轮询**（新手写法）：`loop()` 里反复 `digitalRead(BTN_PIN)` 查状态。三个问题：

1. **浪费 CPU**：不按键时也在空转查询
2. **实时性差**：如果 loop 里有耗时操作（比如一个 100ms 的任务），按下到响应可能延迟 100ms+，甚至错过
3. **可能丢事件**：按键按下到松开可能只有几十 ms，如果读的间隔比这长，事件就漏了

**中断**：硬件检测到边沿变化 → 立即暂停主循环 → 跳 ISR → 执行完返回主循环继续。

```
主循环:  A → B → C → D → E
              ↑ 按键按下（硬件打断）
              ISR 执行（几微秒）→ 返回
```

**本质：同步轮询 vs 异步事件。** 类比：服务员反复巡桌问「需要什么吗」（轮询）vs 顾客按铃（中断）。D1 的 LED 用轮询没问题（自己控制自己），但**外部输入**（按键/传感器）用轮询就浪费——你不知道它什么时候来。

### 2.2 attachInterrupt 注册了什么

```cpp
attachInterrupt(digitalPinToInterrupt(BTN_PIN), onButtonPress, FALLING);
```

芯片内部维护一张「中断表」：**引脚 → ISR 函数指针 + 触发模式**。硬件中断控制器（ESP32 的 GPIO 中断矩阵）在检测到引脚电平变化时，查表找到对应 ISR 并跳转。这张表是芯片外设，不占 CPU——这就是「硬件事件」的含义。

触发模式：

| 模式 | 触发时机 |
|------|---------|
| RISING | 上升沿（LOW→HIGH） |
| FALLING | 下降沿（HIGH→LOW） |
| CHANGE | 任意变化（两个沿都触发） |
| LOW | 电平为低期间持续触发 |

### 2.3 ISR 的硬规则——为什么必须「短」

ISR 执行期间发生了什么：**主循环挂起 + 同/低优先级中断挂起**。这意味着：

- `delay()` 是忙等循环 → 系统**卡死在 ISR 里**，外面一切停摆 → 超过看门狗（WDT）阈值触发**复位**。ESP32 默认看门狗会真的重启芯片。
- `Serial.print()` 耗时（串口外设写 + 缓冲等待）→ 违反「短」原则
- `malloc`/`new`（内存分配）→ 涉及堆锁，可能死锁

**正确姿势：置标志位 + 记录时间戳，其他全留给主循环。** 这就是生产者-消费者模式：

```
ISR（生产者）: btnPressed = true;      ← 只做这两件事
loop（消费者）: if (btnPressed) { 处理 } ← 打印/逻辑全在这
```

### 2.4 volatile——编译器优化陷阱

编译器优化（`-O2`）会把「循环内没被修改的变量」缓存进寄存器，避免反复读内存：

```cpp
// 不加 volatile 的隐患
while (!btnPressed) { }   // 编译器：循环里 btnPressed 没变 → 读一次缓存进寄存器
                          // → 中断改了内存里的 btnPressed，循环还在读寄存器旧值 → 死循环
```

`volatile` 告诉编译器：**这个变量可能被外部（中断/硬件）修改，每次使用都必须重新从内存读**。

类比迁移：Python 多线程里共享变量的**可见性**问题（一个线程改、另一个线程看不到最新值）。volatile 解决可见性；ESP32 上 32 位对齐的 bool/unsigned long 读写是原子的，这里够用。

### 2.5 防抖——物理噪声的工程处理

机械按键内部是金属簧片，按下瞬间 **5-20ms 内会弹跳**（高低电平反复跳变）。不做防抖，一次按下可能触发 3-5 次中断。

**方案 A（新手，坏）**：检测到按下 → `delay(10)` → 再读一次确认
- `delay` 是阻塞的 → 浪费 CPU
- delay 期间如果又按下 → **丢事件**
- 而且 delay 在 ISR 里=灾难（见 2.3）

**方案 B（本 demo，好）**：时间戳过滤——记录上次有效触发时刻，间隔 <50ms 的边沿一律忽略：

```cpp
if (now - lastTrigger > DEBOUNCE_MS) {  // 距上次有效触发 <50ms = 抖动
  lastTrigger = now;
  btnPressed = true;
}
```

非阻塞、主循环零等待、且代码在 ISR 里执行也足够短（比较+赋值，微秒级）✅。

**工程思维**：防抖是典型的「对物理噪声做信号过滤」——量化里叫去重/冷却（trade-pulse 的 cooldown 机制同构），爬虫里叫请求去抖。

### 2.6 为什么 FALLING + 内部上拉

电路：`D4 ── 按键 ── GND`，`INPUT_PULLUP`（内部上拉，省一个电阻）：

- 不按：引脚被内部上拉电阻拉到 HIGH
- 按下：按键接通 GND → LOW
- 按下瞬间 = **下降沿（FALLING）** ✅

为什么不是 RISING（松开沿）？松开瞬间弹簧回弹抖动更剧烈，且「按下」才是动作意图。为什么不用 CHANGE？它会触发两次（按下+松开），还要额外状态判断。

### 2.7 IRAM_ATTR——ESP32 特有的一课

ESP32 的程序代码默认存储在 Flash，CPU 通过 XIP（就地执行）映射读取。**中断发生时如果主循环正巧在从 Flash 取指/读常量，而 ISR 又要取指 → 总线冲突**（Flash 访问不是原子的）。

`IRAM_ATTR` 把 ISR 放进内部 RAM（IRAM），取指不经过 Flash → 无冲突。**工程含义：带 WiFi/蓝牙（FreeRTOS 任务多、Flash 访问频繁）的 ESP32 项目，ISR 必须加 IRAM_ATTR**——这就是为什么真实产品代码里这个修饰符是标配。

## 3. 类比迁移（用你熟悉的领域）

| 嵌入式概念 | 你的已知世界 |
|-----------|-------------|
| 轮询 vs 中断 | 爬虫轮询 API vs webhook/回调推送（事件到达才通知） |
| ISR 置标志 + loop 消费 | 生产者-消费者模式（MQ 解耦，队列缓冲） |
| volatile | 多线程共享变量的可见性（一个线程改、另一个要能看到） |
| 防抖时间戳过滤 | 量化信号去重/冷却（trade-pulse cooldown）；爬虫请求去抖 |
| FALLING 只关心下降沿 | 事件驱动只订阅关心的事件类型，忽略其余 |
